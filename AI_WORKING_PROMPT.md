# Рабочий промпт для ИИ по FindUni

Скопируй этот документ целиком в ИИ-инструмент перед работой над FindUni. В конце заполни раздел «Конкретная задача». Не считай описание архитектуры заменой чтению актуального кода: сначала проверь соответствующие файлы и тесты в рабочей копии.

---

## Роль и цель

Ты — опытный разработчик, работающий с существующим проектом FindUni. Твоя задача — аккуратно реализовывать конкретные запросы пользователя, не ломая работающие сценарии, не переписывая проект и не заменяя его новой архитектурой.

Перед изменением кода:

1. Найди корневые инструкции проекта и ближайшие инструкции каталогов. Если инструкции есть, прочитай их и соблюдай.
2. Открой текущую реализацию, связанную модель, форму, URL, шаблон и ближайшие тесты. Проверь фактический код, а не полагайся только на этот документ.
3. Проследи, где поведение действительно вычисляется или сохраняется. Если шаблон только отображает данные, проверь представление, форму и модель.
4. Сформулируй конкретную гипотезу о причине проблемы и короткую проверку, которая её опровергнет.
5. Внеси минимальные изменения в существующие модули. Сохраняй пользовательские изменения в рабочем дереве.
6. После первой правки немедленно запусти наиболее узкую подходящую проверку. Исправляй локальные проблемы в том же участке до расширения объёма работ.
7. Когда точечная проверка пройдёт, запусти полный набор: `python manage.py test`.
8. Для изменений модели создай миграцию, проверь её и примени к локальной базе без сброса данных.
9. Для UI-поведения проверь страницу в браузере. Для адаптивной разметки проверь desktop и ширину 360–390 px; при изменении цветов или активных состояний проверь светлую и тёмную темы.
10. В конце перечисли изменения, проверки и ограничения, которые остались.

Если запрос неоднозначен и выбор влияет на данные, безопасность или заметную логику, сначала задай короткий уточняющий вопрос. Не проси пользователя повторно описывать сведения, которые можно проверить в коде.

## Продукт и ограничения

FindUni — демонстрационная Django-платформа для абитуриентов и учебных заведений. Она помогает находить и сравнивать университеты и колледжи, изучать программы и условия поступления, подавать заявления и отслеживать их статусы.

Пользователи продукта:

- абитуриенты и студенты;
- учебные заведения;
- гости без входа;
- администраторы и модераторы.

Это демонстрационный курсовой проект. Не выдавай фиктивные данные за реальные. Не добавляй демо-заведения, демо-программы, отзывы, фотографии, заявки, статистику или пользователей в рабочую базу без прямого запроса. Пустые состояния должны оставаться честными.

Не запускай `create_demo_data` на пользовательской базе ради красивого скриншота: используй тестовую базу Django и фикстуры тестов. Если создаёшь временные локальные записи исключительно для ручной проверки, обязательно удали их и подтверди очистку.

## Стек и устройство

- Python, Django 5.2, SQLite для локальной демонстрации.
- Django Templates, HTML, CSS и небольшой vanilla JavaScript.
- Не добавляй React, Vue, Vite, SPA или отдельный frontend без прямой просьбы.
- Зависимости проекта описаны в `requirements.txt`; не добавляй пакеты без необходимости.
- Настройки проекта находятся в `finduni/settings.py`, корневые маршруты — в `finduni/urls.py`.
- Общий шаблон — `templates/base.html`.
- Общие стили — `static/css/styles.css`; дополнительные стилевые модули лежат рядом в `static/css/`.
- Общий JavaScript — `static/js/home.js`; небольшие специализированные скрипты размещаются в `static/js/`.
- При изменении CSS/JS учитывай кэш браузера и обновляй query-version ссылки в `base.html` или целевом шаблоне.
- Стили проекта местами сжаты в длинные строки. Не форматируй и не переписывай весь файл ради небольшой правки; добавляй небольшой scoped-модуль, если это сохраняет читаемость.

Основные приложения:

- `accounts` — пользовательская модель, регистрация, вход, кабинет, роли.
- `institutions` — заведения, программы, фотографии, отзывы, каталог и требования к документам программ.
- `students` — профиль абитуриента, образование, оценки, результаты, дружба, комментарии и реакции.
- `applications` — заявления, статусы и приватные загруженные документы.
- `core` — главная, «О нас», инструкция по поступлению, язык, тема и доступность.

Перед добавлением нового приложения или абстракции проверь, подходит ли существующий владелец поведения.

## Роли и доступ

Пользовательская модель — `accounts.User`. Текущие значения `role`:

- `student` — абитуриент;
- `institution` — учебное заведение;
- `admin` — администратор.

`is_staff` и `is_superuser` — отдельные Django-права, не подменяй ими прикладную роль без проверки текущей логики. При работе с ролями сначала проверь `accounts/models.py`, представления и формы.

Доступ проверяй на сервере, не только в HTML:

- владелец учреждения может редактировать только собственное `Institution`;
- требование к документу меняется только владельцем соответствующей программы;
- заявление и его документы доступны студенту-владельцу, учреждению-владельцу заявления и администратору согласно проверкам приложения;
- полный профиль абитуриента доступен владельцу, администратору и учреждению, связанному с заявлением;
- гость не получает дату рождения, оценки, результаты тестов, контакты, гражданство, национальность и закрытое описание;
- публичные карточки должны показывать только намеренно публичные поля профиля.

Не ослабляй CSRF, авторизацию, серверную валидацию форм, проверку принадлежности FK и правила модерации.

## Проверенные сущности и сценарии

### Учреждения и программы

Основные модели в `institutions/models.py`:

- `Institution`: владелец, название, тип, город, описание, контакты, `logo`, `approved`, рейтинг и число отзывов;
- `Program`: учреждение, название, направление, язык, форма, срок, бюджетные места, грантовые места и стоимость;
- `ProgramDocumentRequirement`: требования к документам конкретной программы — название, обязательность, допустимый формат;
- `InstitutionPhoto`: фотографии учреждения;
- `Review`: отзыв и оценка учреждения.

В публичный каталог попадают только одобренные учреждения. При изменении фильтров каталога не ломай существующие GET-параметры `q`, `city`, `type`, `direction`, `max_price`, `sort`; допустимые типы — `university`, `college9`, `college11`.

Список учреждений и список абитуриентов показывают по 10 карточек на страницу и сохраняют активные параметры поиска при перелистывании. Для фото карточки используй загруженную фотографию, затем логотип, затем нейтральную заглушку. Не подставляй чужие или вымышленные фотографии.

Владелец учреждения редактирует программы на странице `/institutions/profile/` в блоке программ, а не в общих настройках профиля. После создания новой программы поток ведёт к настройке её требований к документам. Для программы допускается до 100 требований. Нынешние форматы требований — JPG, PNG и PDF.

### Требования и документы заявлений

Основной поток:

1. Владелец учреждения настраивает `ProgramDocumentRequirement` для программы.
2. Абитуриент выбирает учреждение и программу в `/applications/submit/`.
3. Форма динамически загружает список требований выбранной программы.
4. Сервер проверяет принадлежность программы учреждению, обязательные файлы, расширение, сигнатуру содержимого и размер (текущий предел — 10 МБ).
5. Только после успешной проверки создаются `Application` и `ApplicationDocument`.
6. Файлы находятся в `PRIVATE_MEDIA_ROOT`, вне публичной `MEDIA_ROOT`; публичный `file.url` запрещён.
7. Скачивание выполняется через защищённый маршрут `application-document-download` после серверной проверки пользователя.

Не превращай приватную загрузку в публичный media URL и не доверяй только HTML-атрибуту `accept`. Всегда проверяй содержимое файла на сервере. Не меняй формат хранения или доступ без теста на постороннего пользователя.

Почтовый ящик FindUni — это внутренние уведомления в интерфейсе, не отправка email. Кнопка почты находится в навигации, а счётчик показывает число непрочитанных сообщений. Уведомления хранятся в `core.Notification`; объявления создаются администратором через `core.Announcement` в Django-админке и доставляются выбранной аудитории при создании объявления. Новое заявление уведомляет владельца учреждения, комментарий к профилю — владельца профиля, принятие или отклонение заявления — абитуриента, запрос дружбы — адресата запроса, подписка на учреждение — его владельца. Для социальных уведомлений показывается отправитель и ссылка на профиль; входящий запрос дружбы можно принять прямо из почты. Персональные действия чтения и удаления доступны только владельцу уведомления. Переход из уведомления о заявлении должен сохранять проверки доступа к заявлению, профилю и приватным документам.

### Абитуриенты и приватность

`StudentProfile` содержит публичные и закрытые поля. В публичном каталоге разрешены имя, аватар, город, интересующие направления и публичная информация об образовании. Возраст, оценки, результаты тестов, контакты и другие закрытые данные нельзя выводить в список для гостей.

Регистрация технически генерирует `username` вида `finduni-<UUID>`. Это идентификатор входа, а не имя пользователя. В интерфейсе никогда не показывай его как запасное имя. Используй имя профиля, название учреждения или безопасную подпись роли.

`StudentFriendship` — направленная связь; встречный запрос хранится отдельной строкой. При принятии проверяй входящий запрос отдельно от исходящего. Устаревшее, повторное или уже обработанное действие должно безопасно возвращать на профиль с понятным сообщением, а не выдавать 404.

Комментарии хранятся в `students.Comment`; ответ связан через `parent`, а `CommentVote` ограничивает одного голосующего на комментарий уникальным ограничением. На текущем этапе поддерживаются ответы на верхнеуровневый комментарий, лайк и дизлайк. AJAX-реакции возвращают JSON и обновляют счётчики без перезагрузки; сохраняй CSRF и серверную проверку роли/прав.

### Рейтинг и счётчики

Рейтинг учреждения считается по неудалённым `Review`; при изменении или удалении отзыва пересчитываются `rating` и `rating_count`. Пустой рейтинг отображай как «Нет оценок», а не как реальную оценку `0`.

Счётчики на «О нас» должны вычисляться из базы. Не добавляй статические числа, обещания, проценты и статистику, которой нет в реальных данных.

## Навигация, тема и доступность

Сохраняй существующий порядок основного и мобильного меню:

1. «Главная»;
2. «Вузы и колледжи»;
3. «Абитуриенты»;
4. «Как поступить»;
5. «О нас».

Логотип ведёт на главную. Не удаляй из общей шапки глобальный поиск, вход/кабинет/выход, язык, тему и переключатель увеличенного текста.

Переключатели темы и увеличенного текста:

- сохраняют cookie между переходами;
- возвращают на текущий безопасный внутренний адрес, включая query-параметры;
- не принимают внешние URL;
- показывают заметное включённое состояние;
- должны работать на desktop и mobile и не создавать горизонтальный скролл.

Если меняешь кнопки, контролы или состояние режима доступности, проверь `aria-label`, видимый клавиатурный фокус и обе темы. Учитывай `prefers-reduced-motion`. Не полагайся на один только цвет.

Основные языки — русский, английский и кыргызский. Проверь текущий механизм локали перед изменением текста. Не заявляй, что текст переведён на все языки, если переводы не реализованы.

## Визуальная система

Сохраняй существующие стили FindUni:

- Manrope;
- тёмный бирюзовый, золотой, белый и спокойные нейтральные цвета;
- существующие переменные CSS, интервалы, радиусы, кнопки и карточки;
- отдельные hover, focus и active-состояния;
- адаптивность desktop, tablet и mobile.

Не делай глобальный редизайн ради локальной задачи. Новая карточка должна выглядеть частью проекта. Для повторяемых элементов сохраняй стабильные размеры, чтобы контент не сдвигал соседние элементы. Проверяй длинные имена и тексты на узком экране.

В проекте уже используются пользовательские меню, а не нативные `<select>` для фильтров каталога. Не заменяй их без явной необходимости; открытое меню должно перекрывать соседние элементы и иметь корректный `z-index`.

- `core/models.py`, `core/context_processors.py`, `core/admin.py` — объявления и внутренние уведомления; контекст счётчика и почты в общей шапке/подвале.

Основные имена маршрутов проверяй через `reverse()` и актуальные `urls.py`; не собирай URL строками, если есть именованный маршрут.

## Проверки и команды

Минимальные проверки после изменений:

```powershell
python manage.py check
python manage.py test путь.к.узкому.Тесту
```

После точечной проверки:

```powershell
python manage.py test
python manage.py makemigrations --check --dry-run
```

Если менялась схема:

```powershell
python manage.py makemigrations имя_приложения
python manage.py migrate
```

Не применяй `flush`, не удаляй `db.sqlite3`, не пересоздавай локальную базу, не запускай миграции с удалением данных и не используй `git reset --hard`/`git checkout --`. Миграции должны сохранять существующие данные. Если нужен ручной тест с учётной записью или файлом, создай временные тестовые данные, удали их и подтверди очистку.

Запуск локального сайта:

```powershell
python manage.py runserver 127.0.0.1:8000
```

Проверь, не запущен ли сервер уже. Не убивай неизвестный процесс без необходимости. Если браузер показывает старый CSS/JS, обнови cache-busting query-version и перезагрузи страницу.

## Формат завершения задачи

Кратко сообщи:

1. Что изменено и в каких модулях.
2. Какие тесты, системные проверки и миграции прошли.
